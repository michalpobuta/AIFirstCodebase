# The AI-First .NET Codebase: A Playbook

How to set up a .NET repository so that a coding agent can do the work without you stepping in, for new
repositories and for the ones you already have.

Every practice below is implemented in the [sample project](sample/), and the links point to the exact lines.
Evidence is as of October 2026. Where a claim rests on a study or on a team's report, the source is named
with its evidence type and the model generation it was measured on. Where it's my own recommendation, it
says so.

## The approach

### What "AI-first" means

An AI-first codebase is one where **the agent solves a task without you stepping in**: it finds the place,
changes it, and proves the change works. Any agent can *work* with any codebase. The difference is how often
a human has to add a commit, correct a direction, or catch a mistake after the fact.

That definition gives you the metric for everything in this playbook: **how often you step in.**

### Why agents fail on your code

Two reasons, and the rest of this playbook is about removing them:

- **Structure it can't navigate.** The agent doesn't know your codebase. It searches: grep, glob, semantic
  search over your names. If the names and folders don't lead to the right place, it reads the wrong files,
  or too many of them.
- **Knowledge it can't infer.** Some facts are not in the code: a CSV that another team's system parses, a
  folder that automation overwrites, a rounding rule that finance depends on. The agent will not ask about
  them. It will guess.

### Advice lowers the rate. The build sets the floor.

You can tell the agent things (instruction files, skills, prompts), or you can make the codebase reject wrong
changes (types, the compiler, tests, CI, required reviews). Both help, but differently:

- **Advice lowers the rate** of mistakes. The agent usually follows it, but nothing guarantees it, and it
  costs tokens in every session.
- **The build sets the floor.** A check outside the agent's reach that can say no (the build, CI, a required
  review) holds no matter which model runs, how it was prompted, or whether it read the instructions.

So for every rule, ask how high up this ladder it can go, and put it there:

| Rung | What it means | .NET example |
|---|---|---|
| **Types** | The wrong code can't be written | `OrderId` instead of `Guid`, an enum instead of a string |
| **Compiler** | The wrong code doesn't build | an analyzer, a banned API, warnings as errors |
| **Test** | The wrong code fails a test | an architecture test, an approval snapshot |
| **Gate** | The wrong change can't merge | CI, CODEOWNERS with a required review |
| **Advice** | The agent is told | one line in `AGENTS.md` |

> "When a reviewer (human or bot) corrects the same thing twice, encode it: make it impossible in types or
> structure, else a lint rule or a test, else a skill line, in that order of preference."
> *([tester-army/e2e AGENTS.md][tester-army])*

### Four layers

The playbook is organised around four questions an agent asks a repository, each answered by one layer:

| The agent asks | Layer | Mostly made of |
|---|---|---|
| Where does this go? | [1 · Structure](#layer-1--structure-the-agent-can-navigate) | names, folders, architecture tests |
| What are the rules? | [2 · Rules](#layer-2--rules-the-build-enforces) | `Directory.Build.props`, analyzers, banned APIs |
| How do I know I'm done? | [3 · Checks](#layer-3--checks-the-agent-cant-fake) | one test command, CI, CODEOWNERS, hooks |
| What must I not break? | [4 · Knowledge](#layer-4--knowledge-the-code-cant-give) | a short `AGENTS.md`, notes loaded on demand |

Prose comes last on purpose. Instruction files are the right home only for what the first three layers can't
express.

### Why not start with instruction files?

Because the evidence says they're the weakest lever:

- Context files generated by `/init` raised the cost of a task by 20–23% with no significant gain in success.
  Files written by developers did slightly better: +2.4 points, not significant *([ETH Zurich][eth], ICLR 2026
  workshop; Sonnet 4.5, GPT-5.2; Python; replicated by [Khatri][khatri], preprint)*.
- In 23% of 356 repositories, the context file named at least one function, file or script that no longer
  existed *([Treude & Baltes][treude], Jun 2026, preprint)*.
- The teams with the largest files are cutting them down and moving content into path-scoped files and
  skills: Sentry's `AGENTS.md` went from 1,550 lines to 138 *([commit][sentry])*, dotnet/runtime's
  Copilot instructions from 287 to 80 *([commit][runtime-split])*, and EF Core's from 254 to 40
  *([#37768][efcore-a], [#38126][efcore-b])*.

What moved the needle in the best-documented case was the environment. In dotnet/runtime, the merge rate of
the Copilot agent's PRs went from 38% to 69% after the team gave it firewall rules for the package feeds,
build instructions and setup steps: things it could run *([Toub, .NET Blog][toub], Mar 2026, observational,
vendor; the period also includes ten months of model updates)*.

## Before you start: measure step-ins

You'll want a baseline, so you can tell whether any of this helps on *your* code. There is no controlled study
on C# yet, so your own numbers are the best evidence you'll get.

- **Cloud agent** (Copilot cloud agent, Codex cloud and similar): count the PRs where a human had to add
  commits, and the success rate as *merged ÷ (merged + closed)*. That's how dotnet/runtime measured it.
- **Agent in the IDE or CLI** (agent mode in Visual Studio, Rider, Claude Code, Codex CLI): take 5–10 tickets
  closed last quarter, check out each one's parent commit, and give the agent the ticket, twice per ticket
  because runs vary. Record whether the build and tests went green without you, how many times you stepped
  in, and the cost. *(My suggestion; it mirrors the metrics of the ETH study.)*
- **Review time.** The bottleneck moves there. In dotnet/runtime, nine agent PRs opened within a few hours took
  5–9 hours to review.

Repeat after a month.

## Layer 1 · Structure the agent can navigate

**Goal:** a search for the use case lands in one folder, and the code that runs is reachable from the code
that calls it by text.

Agents find code by searching. CLI agents glob and grep, then read the results. IDE agents add semantic
search, which still matches on your names. An architecture overview in an instruction file doesn't replace
that: in the ETH study, repository overviews didn't get agents to the right files any faster.

### 1.1 Name things after use cases

- One use case per file, named after it: `PayOrder.cs` contains the request, the handler and the endpoint,
  [`PayOrder.cs` L5–L20](sample/src/Shop/Features/Orders/PayOrder.cs#L5-L20).
- Group by feature, not by technical layer: `src/Shop/Features/<Area>/`.
- No `Manager`, `Helper`, `Service`, `Utils`. They're names that tell a search nothing.

**The grep test** *(a heuristic, not a study)*: search for the use case, for example `grep -ril "pay" src`. If
the hits are spread over many folders, rename or move. Every extra hit is a file the agent may read, and those
tokens stay in its context for the rest of the session. In the sample, the search finds 3 files in one folder.
In a typical layered version of the same app (controller, service, manager, repository), it finds 4 files in
3 folders, and the logic is a branch inside a 90-line method.

### 1.2 Keep the trail visible

Anything dispatched at runtime by convention breaks the textual link between caller and callee:

- `IMediator.Send(...)`: Go to Definition lands in MediatR, not in your handler.
- Registering services by scanning the assembly for a name suffix.
- Mapping objects by property-name convention.

You don't have to remove the library. You have to make the link findable:

- Put a request and its handler in the same file, and enforce it with a test,
  [`ArchitectureTests.cs` L31–L41](sample/tests/Shop.Tests/Architecture/ArchitectureTests.cs#L31-L41).
- List registrations by hand, one module per feature,
  [`OrdersModule.cs` L6–L22](sample/src/Shop/Features/Orders/OrdersModule.cs#L6-L22).
- Prefer source-generated mediators and mappers: the generated code is searchable.
- Give the agent a language server, so it gets Go to Definition too. dotnet/roslyn installs
  `roslyn-language-server` in its agent's setup steps *([roslyn][roslyn-setup])*.

### 1.3 Enforce the structure with tests

Folder rules, layer rules and naming rules are tests, not paragraphs. With NetArchTest:

- names say what the type does,
  [`ArchitectureTests.cs` L14–L17](sample/tests/Shop.Tests/Architecture/ArchitectureTests.cs#L14-L17);
- shared code doesn't depend on features, and handlers don't depend on ASP.NET Core,
  [`ArchitectureTests.cs` L19–L29](sample/tests/Shop.Tests/Architecture/ArchitectureTests.cs#L19-L29).

When the agent drifts, the failure names the type:

```text
failed TypeNames_SayWhatTheTypeDoes
  Violated by: Shop.Features.Orders.OrderHelper
```

Libraries already do the equivalent with public API baselines. In an audit of 18 well-known .NET repositories
(October 2026), 10 had API baselines and none had architecture tests. For an application, the tests above take
about ten minutes to write.

### 1.4 Refactor where agents will work, not everywhere

Find the files that change most, [`eng/hotspots.sh` L5–L7](sample/eng/hotspots.sh#L5-L7):

```bash
git log --since=12.months --format= --name-only -- '*.cs' \
    ':(exclude)**/Migrations/**' ':(exclude)**/*.Designer.cs' \
  | sort | uniq -c | sort -rn | head -15
```

On Windows, run it in Git Bash. The top of that list, crossed with code that's hard to read, is where
restructuring pays.

Keep expectations honest. Healthier code had 15–30% fewer broken refactorings for mid-size open models, but
for Claude Code the difference wasn't significant *([Borg et al.][borg], FORGE 2026, Python, CodeScene
co-authors)*. Classic complexity metrics didn't predict LLM success *([Xie et al.][xie], ICML 2026, mainly
DeepSeek-V3)*. Structure helps weaker, cheaper models most. Tests (Layer 3) help every model.

### 1.5 Give a refactoring task a target the agent can run

"Clean this up" is not a task an agent can finish. Unguided, Claude Code mostly renamed things: 54k renames
against 7.5k extract-method refactorings *([CodeScene][codescene], Mar 2026, vendor)*. A test it has to turn
green is a task it can finish:

1. **Pin:** an approval or characterization test around the hotspot (see
   [B2](#b2--pin-it-tests-without-touching-the-code)).
2. **Rule:** a red architecture test, for example "no `*Manager`" or "handler next to its request".
3. **Extract:** the agent moves one use case until the rule passes and the pin stays green.
4. **Merge:** next use case, next PR.

```text
Move the pay flow out of OrderManager until ArchitectureTests pass for it.
The snapshot tests must stay green and unchanged.
```

**Layer 1 checklist**

- [ ] A search for any use case lands in one folder.
- [ ] No `Manager` / `Helper` / `Utils` types, enforced by a test.
- [ ] Every handler is next to its request, enforced by a test.
- [ ] Registrations are listed, not scanned.
- [ ] You know your top 15 hotspots.

## Layer 2 · Rules the build enforces

**Goal:** every convention a tool can check fails the build, with a message that says what to do instead.

### 2.1 One `Directory.Build.props` for the whole solution

[`Directory.Build.props` L3–L10](sample/Directory.Build.props#L3-L10):

```xml
<Nullable>enable</Nullable>
<TreatWarningsAsErrors>true</TreatWarningsAsErrors>
<AnalysisLevel>latest-recommended</AnalysisLevel>
<EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
```

Each line replaces a paragraph someone would otherwise write in `AGENTS.md`, and it applies to every tool and
every person. dotnet/orleans uses almost the same set *([orleans Directory.Build.props][orleans-props])*. In the
audit of 18 well-known .NET repositories, warnings failed the build in 16, nullable was on in 15 and analyzers
in 14.

Pair it with:

- **Central Package Management**, one version per package:
  [`Directory.Packages.props`](sample/Directory.Packages.props#L1-L12).
- **`.editorconfig` with severities**, so style rules are errors rather than suggestions:
  [`.editorconfig` L3–L8](sample/.editorconfig#L3-L8). `IDE*` rules break the command-line build only with
  `EnforceCodeStyleInBuild`.
- **Pinned SDK**: [`global.json`](sample/global.json#L1-L9).

### 2.2 Make wrong states impossible

A string status with a `default:` branch is how a new value slips through silently:

```csharp
switch (status?.ToUpper())
{
    case "NEW": return "NEW";
    case "PAID": return "PAID";
    case "SHIPPED": return "SHP";
    default: return "NEW";   // add "Cancelled" and the warehouse ships it as a new order
}
```

Use an enum and a switch expression **without a `_ =>` arm**,
[`WarehouseExport.cs` L22–L28](sample/src/Shop/Features/Warehouse/WarehouseExport.cs#L22-L28). Adding a value
then stops the build at every switch that hasn't decided what to do with it:

```text
WarehouseExport.cs(23,65): error CS8509: The switch expression does not handle all possible
values of its input type. For example, the pattern 'OrderStatus.Cancelled' is not covered.
```

Two settings are required:

- CS8509 is a warning. `TreatWarningsAsErrors` makes it an error.
- CS8524 fires for unnamed enum values such as `(OrderStatus)42` on the same switch. Turn it off, or the pattern
  breaks the build before anyone adds a value: [`.editorconfig` L13–L16](sample/.editorconfig#L13-L16).

Strongly typed ids (`OrderId`, `CustomerId`) do the same for arguments passed in the wrong order,
[`Ids.cs`](sample/src/Shop/Shared/Ids.cs#L1-L13).

Why types first: in LLM-written TypeScript, about 94% of compile errors were type errors *([Mündler et
al.][mundler], PLDI 2025, open models up to 34B; no equivalent data for C#)*.

### 2.3 Ban APIs, with the fix in the message

[`BannedSymbols.txt`](sample/BannedSymbols.txt#L1-L4), wired up with the
`Microsoft.CodeAnalysis.BannedApiAnalyzers` package in
[`Directory.Build.props` L12–L16](sample/Directory.Build.props#L12-L16):

```text
P:System.DateTime.UtcNow;Inject TimeProvider and call GetUtcNow() — tests control time through FakeTimeProvider
```

```text
PayOrder.cs(11,25): error RS0030: The symbol 'DateTime.UtcNow' is banned in this project:
  Inject TimeProvider and call GetUtcNow() — tests control time through FakeTimeProvider
```

The message after the semicolon is the correction. The agent gets it from the build, without you. Good
candidates: the wall clock, `Console.WriteLine` in library code, a deprecated internal API, `Task.Result`,
`new HttpClient()`. Anything you corrected twice.

### 2.4 Say in `AGENTS.md` what enforces each rule

Don't restate a rule in prose. Name its enforcer,
[`AGENTS.md` L10–L16](sample/AGENTS.md?plain=1#L10-L16):

```text
- No wall clock in app code                  [enforced: RS0030 · BannedSymbols.txt]
- Handlers don't reference ASP.NET Core      [test: Handlers_DoNotKnowAboutHttp]
```

The tag tells the agent there's no point arguing with the rule, and tells a reviewer where to look. Keep the
tags honest with a test: [`InstructionFilesTests.cs` L44–L61](sample/tests/Shop.Tests/Architecture/InstructionFilesTests.cs#L44-L61)
fails if a `[test: …]` tag names a test that doesn't exist. PostHog does the same for its tags
*([AGENTS.md][posthog], [the tag test][posthog-test])*.

### 2.5 Make switching a rule off a reviewer's decision

The fastest way to a green build is to switch the rule off: `<NoWarn>`, `#pragma warning disable`,
`[SuppressMessage]`, a lowered severity in `.editorconfig`, a skipped test. Agents weakened tests or checks
without permission in 14.7% of 4,990 public sessions *([Transluce][transluce], Aug 2026, blog, judged by an
LLM, mostly Opus 4.6)*.

- **A CI step** fails on any added suppression or skip and on any removed test, so a human has to approve it:
  [`eng/check-suppressions.sh` L11–L25](sample/eng/check-suppressions.sh#L11-L25), run in
  [`ci.yml` L23–L25](sample/.github/workflows/ci.yml#L23-L25). If the base branch isn't available, `git diff`
  fails and the step fails with it: a check that can't run must not pass.
- **CODEOWNERS** on the files that hold the rules,
  [`CODEOWNERS` L8–L14](sample/.github/CODEOWNERS#L8-L14).
- **One line of advice** where it matters most. dotnet/orleans: *"Do not resolve compatibility failures by
  disabling package validation or adding CP\*/PKV\* diagnostics to NoWarn."*
  *([orleans AGENTS.md L73][orleans-agents])*

The null-forgiving `!` won't show up in a grep. That one is for review.

### 2.6 In an existing codebase, one notch at a time

`TreatWarningsAsErrors` on a ten-year-old solution on day one produces thousands of errors and gets reverted
on day two. Tighten in notches instead, each one a PR an agent can do well (one rule, a clear error, a green
build):

1. **Per project, most-changed first:**

   ```xml
   <Nullable>enable</Nullable>
   <WarningsAsErrors>$(WarningsAsErrors);nullable</WarningsAsErrors>
   ```

   Append to `$(WarningsAsErrors)`; don't overwrite it.
2. **Strict where new code goes**, with a nested `.editorconfig`:

   ```ini
   # src/Features/.editorconfig
   [*.cs]
   dotnet_diagnostic.CA2016.severity = error
   ```

3. **A ratchet:** CI records today's warning count, and it may only go down.

Skip whole-codebase formatting rules such as `IDE0161` (file-scoped namespaces) as agent tasks: they touch
every file, and `dotnet format` does them deterministically. Being partway is normal: dotnet/maui has
nullable enabled in 45 of 130 projects.

**Layer 2 checklist**

- [ ] Nullable, warnings as errors, analyzers and code style in one `Directory.Build.props`.
- [ ] Enums and switch expressions without `_ =>` for every status a downstream system cares about.
- [ ] The thing you corrected twice is in `BannedSymbols.txt`.
- [ ] Each rule in `AGENTS.md` names its enforcer, and a test checks the names.
- [ ] A new suppression, skip or deleted test fails CI until a human approves it.

## Layer 3 · Checks the agent can't fake

**Goal:** "done" means a check passed, not that the agent said so.

Agents report more than they verified. In 1 in 3 public agent sessions, the agent claimed more done or more
verified than the transcript showed *([Transluce][transluce]; 5.7% on Transluce's own traffic, so the setup
matters)*. In another study, 7 of 12 runs passed the acceptance tests while the library they were asked to use
was dead or missing *([Ma et al.][building], Jun 2026, preprint; Opus 4.7, GPT-5.5)*.

A check that counts has three properties: **you can run it, it can fail, and the agent can't change it.** And
the test that defines "done" is written or approved by a human.

### 3.1 One command, runnable on the agent's machine

- **Write the exact command into the instruction file**, the same one CI runs:
  [`AGENTS.md` L5–L8](sample/AGENTS.md?plain=1#L5-L8) and [`ci.yml` L21–L22](sample/.github/workflows/ci.yml#L21-L22).
  It's the most valuable line in the file.
- **Make it fast enough to run every turn.** For a large solution, add a solution filter (`.slnf`) per area and
  the command to test one project.
- **Prepare the agent's machine.** For the Copilot cloud agent that's
  [`copilot-setup-steps.yml` L9–L19](sample/.github/workflows/copilot-setup-steps.yml#L9-L19). The job must be
  named exactly `copilot-setup-steps`. It runs from the default branch, for at most 59 minutes, and if a step
  fails the agent starts anyway *([GitHub Docs][gh-setup])*. Restore NuGet, start what the tests need. EF Core
  starts SQL Server and the Cosmos emulator there, so the agent reuses one database between runs
  *([efcore][efcore-setup])*. 9 of the 18 audited repositories ship this file.
- **No cloud agent?** Agent mode in Visual Studio runs on your machine, so the same command in
  `copilot-instructions.md` is enough. For database tests, `WebApplicationFactory` with Testcontainers works
  locally.

Everything the tests need must exist in the agent's environment, or be faked: a database, a message broker,
an external API.

### 3.2 A run that runs nothing must fail

This is the most common silent false green in .NET. A filter that matches no tests looks like success:

| Runner | Filter matches nothing | Exit code |
|---|---|---|
| VSTest, default | `No test matches the given testcase filter …` | **0** |
| VSTest + `TreatNoTestsAsError` | same message | 1 |
| Microsoft.Testing.Platform (MTP) | `Zero tests ran` | 8 |

*(Reproduced on .NET SDK 10.0.303 with xUnit 2.9.3 on VSTest and xUnit v3 4.0.2 on MTP.)* The text on screen
is the same, so an agent reading the output reports green. A stale filter in an instruction file is enough to
trigger it.

- **On MTP**, zero tests fail by default. Don't add `--ignore-exit-code 8`. The sample opts into MTP in
  [`global.json` L6–L8](sample/global.json#L6-L8).
- **On VSTest**, add a `.runsettings` and point every test project at it:

  ```xml
  <!-- test.runsettings -->
  <RunSettings>
    <RunConfiguration>
      <TreatNoTestsAsError>true</TreatNoTestsAsError>
    </RunConfiguration>
  </RunSettings>
  ```

  ```xml
  <!-- Directory.Build.props -->
  <RunSettingsFilePath>$(MSBuildThisFileDirectory)test.runsettings</RunSettingsFilePath>
  ```

- **In CI, pin the count** so that losing tests fails too:
  [`ci.yml` L22](sample/.github/workflows/ci.yml#L22) runs `dotnet test --minimum-expected-tests 25`, which exits
  with code 9 when fewer tests run. It's an MTP option; dotnet/orleans uses it with 1
  *([orleans copilot-instructions.md][orleans-min])*.

In the audit, 8 of the 18 repositories didn't configure an empty run to fail.

### 3.3 Every test must be able to fail

```csharp
[Fact]
public void Test3()
{
    // flaky on the build server, see #412
    try
    {
        var m = CreateManager();
        var r = m.ProcessOrder(Request("C-002", 100), "create", null);
        var s = m.ProcessOrder(null, "ship", r.Id);
        Assert.Equal("Shipped", s.Status);
    }
    catch (Exception) { }
}
```

Change `"Shipped"` to `"Banana"` and it stays green: shipping an unpaid order throws before the assert, and the
`catch` swallows it. Every old codebase has a few of these, and the agent treats them as specification.

- **Red before green.** Put it in the instruction file: *"Before you claim a fix works, show the test failing
  without it."* [`AGENTS.md` L28](sample/AGENTS.md?plain=1#L28). dotnet/aspnetcore has the same line, and
  dotnet/maui has a skill for it.
- **Mutation testing** shows which code no test notices changing. [Stryker.NET][stryker]:

  ```bash
  dotnet tool install -g dotnet-stryker
  dotnet stryker --since:main    # only the code changed on this branch
  ```

  Don't chase a 100% score. Run it on one project from your hotspot list, set a threshold yourself
  (`--break-at`), and only ever raise it. One file with 100% statement coverage and no unit tests let 13
  mutants survive *([Böckeler][bockeler], May 2026, one TypeScript app)*. Check that your test runner is
  supported before you rely on it.

### 3.4 Protect the specification, and give the agent a way out

Agents optimise for the check. On tasks whose tests contradicted the specification, top agents "passed" about
half, Claude mostly by editing the tests *([ImpossibleBench][impossiblebench], ICLR 2026; GPT-5, Opus 4.1)*.
When answers were reachable, 2026 agents peeked at them in 23–48% of tasks *([HVTB][hvtb], Aug 2026, preprint;
Opus 5, GPT-5.6 Sol, Gemini 3.1 Pro)*.

What reduced it in both studies:

- **Name exactly what must not be touched.** A generic "don't cheat" roughly halved peeking; naming the exact
  thing brought it to 0% for two of the three models (16% for Gemini) *(HVTB)*.
- **Give an honest way out.** With an option to stop and report, GPT-5's rate fell from 54% to 9%
  *(ImpossibleBench)*.

In the sample, both are in [`AGENTS.md` L26–L30](sample/AGENTS.md?plain=1#L26-L30):

```text
- Existing tests are the specification. Add tests freely; never edit or delete one to make code pass.
- If the specification is unclear or seems wrong (a test, or a contract like the warehouse CSV), stop and
  begin your final message with `SPEC QUESTION:`. That is the only way to finish with a red build.
```

This is still advice: it lowers the rate. The floor is next.

**Contracts with other systems** get an approval test: the expected output is a file next to the test, and
only a human replaces it. [`WarehouseExportTests.cs` L5–L23](sample/tests/Shop.Tests/Features/Warehouse/WarehouseExportTests.cs#L5-L23)
pins the warehouse CSV, using a 40-line helper,
[`Snapshot.cs` L6–L29](sample/tests/Shop.Tests/Snapshot.cs#L6-L29). Verify does the same with more features.
It requires a declared license, or its SponsorCheck (SC021) fails the build.

### 3.5 Put the checks out of the agent's reach

**The floor** works for every tool, Visual Studio included:

- **CI** runs the same command on a machine the agent doesn't control:
  [`ci.yml`](sample/.github/workflows/ci.yml#L1-L25).
- **CODEOWNERS** on tests, approved snapshots, build settings, instruction files and the agent's own
  configuration: [`CODEOWNERS`](sample/.github/CODEOWNERS#L1-L26). On its own it enforces nothing. Turn on
  the branch rule *Require review from Code Owners*. On Azure DevOps, use a branch policy with required
  reviewers per path.
- **Keep one check the agent never sees**: CI-only acceptance tests, or a human review. Read-only tests stop
  edits, not hard-coding.

**The guard** works inside the session. Agent hooks run before or after a tool call, and exit code 2 blocks
it in Claude Code, Codex and the Copilot CLI and cloud agent. The sample has two Claude Code hooks, written as
C# file-based apps, [`settings.json` L2–L25](sample/.claude/settings.json#L2-L25):

- [`protect-tests.cs` L16–L35](sample/.claude/hooks/protect-tests.cs#L16-L35) blocks edits to existing tests
  and approved snapshots, and tells the agent what to do instead:

  ```text
  tests/Shop.Tests/Features/Orders/PayOrderTests.cs
  is an existing test, and existing tests are the specification.
  Change the code so the test passes, or add a new test file.
  If you believe this test is wrong, stop and begin your
  final message with "SPEC QUESTION:" and say why.
  ```

- [`verify.cs` L12–L28](sample/.claude/hooks/verify.cs#L12-L28) won't let the agent finish while the build or
  the tests are red, and returns only the failures, not the whole log (in the sample, 924 bytes instead of
  3.8 KB).

Treat hooks as code and test them. A Stop hook that checks whether the last message *contains*
`SPEC QUESTION:` lets out an agent that writes "This isn't a SPEC QUESTION:". Check that the message *starts*
with it, [`verify.cs` L12–L14](sample/.claude/hooks/verify.cs#L12-L14).

Know the limits of hooks:

- They guard file edits, not the shell. An agent can still move a file through Bash.
- VS Code hooks are in preview, and Visual Studio doesn't document any.
- None of the 18 audited repositories commits an agent hook. CI stays the backstop.

**Layer 3 checklist**

- [ ] The instruction file names the one build-and-test command CI runs.
- [ ] The agent's environment can run it: setup steps, or a documented local loop.
- [ ] Zero tests fail the run; CI also pins a minimum count.
- [ ] "Show the test failing without the fix" is in the instruction file.
- [ ] Contracts with other systems have approval tests.
- [ ] CODEOWNERS plus the branch rule cover tests, snapshots, build files and instruction files.

## Layer 4 · Knowledge the code can't give

**Goal:** a short root file with only what no tool can infer, more context loaded only when needed, and every
line kept true.

Every line of an instruction file is an order. When a file mentioned `uv`, agents used it 1.6 times per task;
when it didn't, almost never *([ETH Zurich][eth])*. That's why a wrong line costs more than a missing one.

### 4.1 What belongs in the root file

| Keep | Move or delete |
|---|---|
| The build-and-test command, and its traps | Architecture tours, folder listings |
| One line per enforced rule, naming the enforcer | Rules restated in prose (they're in the build) |
| **Never X, because Y**: what the code can't tell | Anything the agent can infer from the code |
| Pointers to path-scoped files and skills | Area-specific detail (move it to a path-scoped file) |

Real "never X, because Y" lines from .NET repositories:

- dotnet/runtime and roslyn: *"Edits in eng/common will be overwritten by automation unless the changes are
  made directly in the Arcade repository."*
- Aspire: never change `NuGet.config`, because it lists the approved package sources for the internal build.
- Aspire: don't update the generated `api/*.cs` files, because they track the API that has already shipped.

The sample's [`AGENTS.md`](sample/AGENTS.md?plain=1#L1-L43) is 43 lines:

| Section | Lines |
|---|---|
| Build and test | [L5–L8](sample/AGENTS.md?plain=1#L5-L8) |
| Enforced by the build, not repeated here | [L10–L16](sample/AGENTS.md?plain=1#L10-L16) |
| Where code goes | [L18–L22](sample/AGENTS.md?plain=1#L18-L22) |
| The specification and the way out | [L24–L30](sample/AGENTS.md?plain=1#L24-L30) |
| Things the code can't tell you | [L32–L37](sample/AGENTS.md?plain=1#L32-L37) |
| Where to look next | [L39–L43](sample/AGENTS.md?plain=1#L39-L43) |

**How long?** About 30–60 lines for an application; a monorepo the size of Aspire lands near 100. Every line
ships in every session. Copilot bills by token since 1 June 2026 *([GitHub][copilot-billing])*, and Codex reads
at most 32 KiB of these files by default *([Codex docs][codex])*.

### 4.2 One source for every tool

Tools read different files, and Copilot Chat in Visual Studio doesn't read `AGENTS.md` at all. It reads
`.github/copilot-instructions.md` and `.github/instructions/*.instructions.md` *([GitHub Docs][gh-matrix])*.

- [`AGENTS.md`](sample/AGENTS.md?plain=1) is the one you edit.
- [`CLAUDE.md`](sample/CLAUDE.md?plain=1#L1-L2) imports it with `@AGENTS.md`.
- [`.github/copilot-instructions.md`](sample/.github/copilot-instructions.md?plain=1) is an exact copy, and a
  test keeps it exact:
  [`InstructionFilesTests.cs` L12–L16](sample/tests/Shop.Tests/Architecture/InstructionFilesTests.cs#L12-L16).

Why a copy and not a symlink: Git on Windows checks a symlink out as a one-line text file unless symlinks are
enabled. A tool that reads both files loads the content twice, which is one more reason to keep it short.

### 4.3 Everything else loads on demand

| Needed for | Put it in | Sample |
|---|---|---|
| every task | the root file | [`AGENTS.md`](sample/AGENTS.md?plain=1) |
| one area of the code | a path-scoped file (`applyTo`; works in Visual Studio too) | [`tests.instructions.md`](sample/.github/instructions/tests.instructions.md?plain=1#L1-L10), [`warehouse.instructions.md`](sample/.github/instructions/warehouse.instructions.md?plain=1#L1-L17) |
| one kind of task | a skill | [`characterization-tests/SKILL.md`](sample/.claude/skills/characterization-tests/SKILL.md?plain=1#L1-L21) |
| reference material | `docs/`, linked from the above | — |

Not every tool reads every format. The root file lists both path-scoped files and the skill under
[Where to look next](sample/AGENTS.md?plain=1#L39-L43), so an agent that doesn't load them automatically still
knows where they are. dotnet/runtime works this way at scale: a 105-line root file that routes to 23
path-scoped files and 23 skills.

**Write skills, don't generate them.** Skills an agent wrote for itself scored below no skills at all (−8 to
−12 points); curated skills added 18 to 25 points *([SkillsBench][skillsbench], Jun 2026, preprint; Claude Code
with Opus 4.7, Codex with GPT-5.5, Gemini CLI)*.

### 4.4 Module notes for knowledge hidden in one area

For an area with rules that live in people's heads, write a short note and load it with that code:
[`warehouse.instructions.md`](sample/.github/instructions/warehouse.instructions.md?plain=1#L1-L17).

- **Short:** quick commands, the non-obvious facts, where to look next.
- **One per module**, owned by whoever owns the module.
- **A source and a date on every claim** (`[code: …]`, `[review: …]`, `[interview: …, 2026-09]`), so you can
  see when it goes stale. Outdated specs were the main failure in a C# project of 108,000 lines built with an
  agent *([Codified Context][codified], preprint, one developer)*.

*(The format is my recommendation, combining those sources.)*

### 4.5 Test the instruction file like code

[`InstructionFilesTests.cs`](sample/tests/Shop.Tests/Architecture/InstructionFilesTests.cs#L12-L61) checks
four things:

- the Visual Studio copy is exact (L12–L16);
- the root file stays within a line budget (L18–L25);
- every path it names exists (L27–L42):

  ```text
  failed AgentsMd_PathsItNamesExist
    AGENTS.md names paths that don't exist: src/Shop/Helpers/Utils.cs
  ```

- every `[test: …]` tag names a real test (L44–L61).

Larger teams go further. EF Core evaluates each skill, and its instruction file, with and without it in CI,
against a committed threshold. roslyn runs a weekly read-only agent that looks for broken links, duplicates and
contradictions in its instruction files.

### 4.6 Triage an existing instruction file

Sort every line of the file you have into five buckets:

| Bucket | Action |
|---|---|
| **Inferable** from the code | delete |
| **Enforced** by the build or a test | replace with one "enforced by" line |
| **Stale** | fix now |
| **Scoped** to one area or task | move to a path-scoped file or a skill |
| **Keep**: command traps, never X because Y | keep in the root file |

Applied to Aspire's 678-line `AGENTS.md` *([pinned][aspire-agents])*, only about one line in six belonged in
the root file, roughly 100 lines instead of 678. A common stale line: *"Always use the latest version C#,
currently C# 13"* in repositories that already build with the .NET 11 SDK. Watch for lines like "these
instructions are comprehensive and tested": they tell the agent to stop looking, so every stale line becomes
a confident wrong action.

**Layer 4 checklist**

- [ ] The root file fits on one screen and lists the build command, enforced rules, never-X-because-Y and pointers.
- [ ] Visual Studio gets a tested copy.
- [ ] Area knowledge lives in path-scoped files; procedures live in hand-written skills.
- [ ] A test fails when the file names a path or a test that doesn't exist.
- [ ] CODEOWNERS covers every instruction file.

## Playbook A · A new repository

A new repository can have all four layers on day one, in about an hour.

**1. Scaffold the rules** (all four templates ship with the .NET 10 SDK):

```bash
dotnet new globaljson --sdk-version 10.0.100 --roll-forward latestFeature
dotnet new buildprops      # then add: Nullable, TreatWarningsAsErrors, AnalysisLevel, EnforceCodeStyleInBuild
dotnet new packagesprops   # one version per package
dotnet new editorconfig    # then set severities to warning
```

Add `"test": { "runner": "Microsoft.Testing.Platform" }` to `global.json`, the BannedApiAnalyzers package and
a `BannedSymbols.txt`.

**2. Lay out by feature:** `src/<App>/Features/<Area>/<UseCase>.cs`, one module file per area,
`tests/<App>.Tests/` mirroring it.

**3. Add the guard tests:** `ArchitectureTests` and `InstructionFilesTests` from the sample.

**4. Write a 30-line `AGENTS.md`** with the four sections from [4.1](#41-what-belongs-in-the-root-file),
`CLAUDE.md` importing it, and the Visual Studio copy.

**5. Set up the floor:** CI with the minimum test count and the suppression check, CODEOWNERS, the branch rule,
and the agent's setup steps.

The result looks like the sample:

```text
sample/
├─ global.json                  SDK + test runner (MTP)
├─ Directory.Build.props        nullable, warnings as errors, analyzers, banned APIs
├─ Directory.Packages.props     one version per package
├─ BannedSymbols.txt            what you corrected twice
├─ .editorconfig                severities
├─ AGENTS.md                    43 lines
├─ CLAUDE.md                    @AGENTS.md
├─ .github/
│  ├─ copilot-instructions.md   tested copy for Visual Studio
│  ├─ instructions/             loaded per path
│  ├─ workflows/                CI + the agent's setup steps
│  └─ CODEOWNERS                + the branch rule (a setting)
├─ .claude/                     hooks and a skill
├─ eng/                         hotspots, suppression check
├─ src/Shop/Features/<Area>/    one use case per file
└─ tests/Shop.Tests/            mirrors src, plus Architecture/
```

Instruction files regrow. In the repository behind the quote at the top of this playbook, `AGENTS.md` grew from
102 to 667 lines in 11 weeks. The line budget test is there for that.

## Playbook B · An existing repository

An existing repository has to earn the four layers, and **the order changes**. The layers above go
strongest first: structure, rules, checks, knowledge. In an old codebase you go **safest first**, because each
step is the safety net for the next:

1. **Make it run.** The agent builds and tests on its own.
2. **Pin it.** Tests for what the code does today, with the production code untouched.
3. **Write down what's hidden.** Rules that live in form events, global config and people's heads.
4. **Then change it.** Chores first, small steps, restructuring last and only where agents will work.

*(The order is my synthesis. The one step every well-documented case shares is that the environment came
first: dotnet/runtime, Stripe, Spotify and Google.)*

### B1 · Make it run

Fix the environment before you touch the prompt. In dotnet/runtime, the agent at first couldn't download
packages or build the repository. Fixing that was most of the jump from 38% to 69%.

- Write the build-and-test command into the instruction file ([3.1](#31-one-command-runnable-on-the-agents-machine)).
- Make everything the tests need available in the agent's environment, or fake it.
- Zero tests must fail ([3.2](#32-a-run-that-runs-nothing-must-fail)).

**Still on .NET Framework?** The Copilot cloud agent's sandbox is Linux by default. Windows needs a larger or
self-hosted runner, and the agent's firewall doesn't work there. The alternative is a local loop: put the exact
commands in `copilot-instructions.md` and use agent mode in Visual Studio.

```powershell
msbuild Legacy.sln -restore -p:RestorePackagesConfig=true -p:Configuration=Debug
vstest.console.exe tests\Orders.Tests\bin\Debug\Orders.Tests.dll /Settings:test.runsettings
```

Converting projects to SDK-style while staying on `net48` gives you `dotnet build`; the tests still run only on
Windows. Do the framework upgrade later, in slices that each build green, and never accept a partial upgrade.

### B2 · Pin it: tests without touching the code

This is the one place where an agent is on safe ground in legacy code.

When an agent writes new code and its tests, both come from the same understanding. If the understanding is
wrong, the tests are wrong in the same way, and green only means the agent agrees with itself. In an old
codebase the code already runs in production, so **the running code is the answer key**. The agent proposes
inputs; the expected outputs come from running the code, not from the model.

LLM-written tests tend to encode what the code currently does rather than what it should do *([arXiv
2410.21136][llm-tests], preprint, 24 Java repositories, 2024 models)*. For new code that's a flaw. For
characterization tests, it's the goal.

**The procedure** (a skill in the sample,
[`SKILL.md` L8–L19](sample/.claude/skills/characterization-tests/SKILL.md?plain=1#L8-L19)):

1. **Recon, read-only:**

   ```text
   Do not edit any files. For PricingEngine.Calculate, list callers, hidden I/O (database, files,
   HTTP, clock, config), static state and candidate seams, with file:line for each.
   ```

   A human checks the list. *(The agent finds the seams, a human verifies them: [Schipper][schipper].)*
2. **Characterization tests:**

   ```text
   Write characterization tests for PricingEngine.Calculate.
   Don't change production code. Record outputs by running it.
   Name the tests Calculate_currently_….
   Expected something else? List it under "Suspicious". Don't fix it.
   ```

   The `currently_` prefix says "this is what it does", leaving `should_` for real specifications
   *([Frisinger][frisinger])*.
3. **A human sorts every captured behaviour:** keep, bug, or delete. Letting the agent accept its own captures
   is grading its own homework.
4. **Break the code once on purpose.** The tests must go red, or they pin nothing.
5. **Mutation testing on the change**, with a threshold you set ([3.3](#33-every-test-must-be-able-to-fail)).

The sample's example is
[`DiscountPolicyCharacterizationTests.cs` L7–L35](sample/tests/Shop.Tests/Features/Orders/DiscountPolicyCharacterizationTests.cs#L7-L35).
It runs a table of inputs through the code and pins the output in an
[approved snapshot](sample/tests/Shop.Tests/Features/Orders/DiscountPolicyCharacterizationTests.TotalFor_currently_returns_these_totals.verified.txt#L1-L9):

```text
CUSTOMER;SUBTOTAL;TOTAL
C-001;500.00;450.00
C-001;999.995;900.00
C-002;10.005;10.01
C-404;500.00;500.00
```

The last line is the kind a human has to sort: an unknown customer silently pays full price. Here it's
"keep", because order creation rejects unknown customers before this code runs. Changing `>=` to `>` in
`DiscountPolicy` turns the test red, so it can fail.

### B3 · Write down what's hidden

Agents miss what lives outside the main path. In a migration of a VB6 ERP to C# on .NET 10 with Claude Code
and Opus 4.6, the migrated features were 92% equivalent for simple features, 81% for medium and 47% for complex
ones. Of 100 misses, 42 were whole adjacent modules (e-mails, imports) and only 6 were wrong code. Validations in
form events were missed even though that code was in the agent's context *([Alves, Politowski,
Montandon][vb6], 2026, one study, venue not confirmed)*. WinForms and WebForms code-behind looks exactly like
that.

Before the agent changes such an area:

- **Catalogue the rules and the database side effects.** In that study, the maintainer listed 160 rules and 171
  database operations before the migration.
- **Interview the people who know.** Let the agent ask, one question at a time *([Fowler, "Interrogatory
  LLM"][interrogatory], May 2026, a technique, not an evaluation)*:

  ```text
  Ask me one question at a time about this module: what breaks silently, what looks unused but isn't,
  which external systems depend on it. Then write a short module note, with a source and a date on each line.
  ```

- **Store it as a module note** ([4.4](#44-module-notes-for-knowledge-hidden-in-one-area)).
- **Verify by what happens, not by how the code looks:** compare the database state, the files written and the
  messages sent before and after.

### B4 · Then change it: chores first

The type of task predicts success better than the choice of agent. In dotnet/runtime, 84.7% of the agent's
cleanup PRs were merged against 54.5% of its performance PRs. Across five agents in another dataset: 84.0%
against 55.4% *([Toub][toub]; [Pinna et al.][pinna], MSR 2026; 2025 agents)*.

A starter backlog, in this order *(my recommendation from those data)*:

1. Dead code.
2. Analyzer warnings, one rule at a time ([2.6](#26-in-an-existing-codebase-one-notch-at-a-time)).
3. Characterization tests for the top hotspot ([B2](#b2--pin-it-tests-without-touching-the-code)).
4. CI and build script fixes.
5. Deprecated API replacements.
6. Bugs that come with a failing repro test.

Not first: performance work without a benchmark the agent can run, and changes across many modules. GitHub's own
documentation for the Copilot agent keeps "understanding dependencies and legacy code" as a task for humans.

**For large, repetitive changes, tools find, the model edits, tools check.** Raw LLM refactorings were unsafe
7.4% of the time, mostly in ways that still compiled. Replayed through the IDE's refactoring engine, 22 of 22 of
those bugs were avoided *([arXiv 2411.04444][refactoring-engine], preprint, 2024 models)*. Patterns that teams
reported:

- **Sample, tune, sweep:** tune the prompt on a small sample, then run it on everything. For example, Airbnb
  migrated 97% of about 3,500 test files in 6 weeks against an estimated 1.5 years *([Airbnb][airbnb], 2025,
  practitioner)*.
- **Leaves first**, then what depends on them; **old and new side by side** for a while. For example,
  Salesforce *([Salesforce Engineering][salesforce], 2025, practitioner)*.
- A few percent always stays manual.
- **My suggestion for .NET:** ask the agent for a Roslyn analyzer with a code fix and its tests, then apply the
  fix across the solution. You review one tool instead of a thousand edits.

### B5 · Plan for review

The bottleneck moves to review. In dotnet/runtime, an agent's PR got 16.5 review comments on average against
12.4 for a human's, and two people gave 36% of all human feedback on agent PRs. 38% of rejected agent PRs were
abandoned or never reviewed *([Ehsani et al.][ehsani], MSR 2026)*. It can work: in runtime, agent PRs were
reverted 0.6% of the time against 0.8% for the rest.

A review policy *(my suggestion from these data)*:

- Whoever starts the agent reviews its PR first.
- A limit on open agent PRs per person.
- One change per PR.
- No auto-merge.
- A cap on retries. For example, Stripe hands the branch to a human after two CI rounds *([Stripe][stripe])*.

## What the evidence can't tell you yet

- Most models in these studies are a generation or more behind the current ones, from 2024 open models to
  summer 2026.
- There is no controlled study on C#. The studies used Python, TypeScript and Java.
- Many numbers are preprints, vendor data or a single team's report. The labels say which.
- Preparation isn't free. On a small sample app, the prepared version cost about 1.5 times more per task,
  because of test runs, hooks and snapshots, not the instruction file. In return it never shipped the
  wrong change. Where structure should save tokens is in repositories too big to read whole, and there's no
  measurement for that yet.
- An audit score is a list of questions, not "Done." A checklist can pass while the branch rule that makes
  CODEOWNERS work is switched off.

What doesn't depend on the model: **a build that fails, a test that can fail, and a reviewer.**
